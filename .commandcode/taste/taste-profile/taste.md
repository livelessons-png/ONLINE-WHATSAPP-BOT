# Taste Profile
- Provides raw terminal/log output as evidence when reporting issues, rather than paraphrasing or summarizing. Confidence: 1.0
- Uses very terse, informal, abbreviated language when asking about errors (e.g., "why this resolve" or "hey fiix thiis n" instead of full sentences). Confidence: 0.9
- Expects explicit verification/confirmation that file edits actually persisted and took effect, not just that they were attempted. Confidence: 0.8
- Does NOT want the assistant to run diagnostic shell/PowerShell/curl/Python commands on their machine. Instead, make the correct code changes and let the user test themselves. Confidence: 0.9
- Communicates feature requests as structured, numbered rule lists with bullet-point specifics (e.g., "1. SILENT DROP... 2. SILENT DROP...") rather than open-ended descriptions. Confidence: 0.8
- Provides complete, copy-paste-ready code blocks when requesting changes, rather than describing changes in prose. Confidence: 0.8
- Prefers production-ready, robust code with defensive edge-case handling (timeout retries, cold-start handling, comprehensive intent/keyword lists, input sanitization). Confidence: 0.7
- Prefers cloud-hosted/serverless architecture over local development — wants to eliminate local dependencies entirely and offload work to cheap/free cloud services (e.g., Render Free, Apps Script, MongoDB Atlas). Confidence: 0.8
- Prefers routing email notifications (escalations, alerts) through Google Apps Script rather than external email APIs (e.g., Brevo), because Apps Script has native access to the institution's Gmail/Workspace account, allowing emails to come directly from the institutional domain (@miva.university) without third-party API keys. Confidence: 0.7
- Embeds meta-instructions and inline reminders directly inside code snippets when requesting changes, rather than writing them as separate follow-up messages. Confidence: 0.6
- Uses external uptime monitoring services (e.g., cron-job.org pinging every 10 minutes) to keep Render Free tier services awake and prevent cold-start sleep. Confidence: 0.8
- Aggressively configures services to stay within free-tier resource limits — uses lightweight engines (e.g., NOWEB instead of Puppeteer), caps Node heap via NODE_OPTIONS, and directs ephemeral file storage to /tmp to avoid RAM/disk blowouts on 512MB instances. Confidence: 0.7
- Cares about proper Python code structure and indentation — notices and requests correction of misplaced imports, broken indentation, or syntax issues inside function bodies. Confidence: 0.8
- Diagnoses the root cause of bugs (e.g., mismatched tuple unpacking lengths from an API call) and provides the exact defensive fix pattern alongside the explanation, rather than simply describing the symptom and asking for a fix. Confidence: 0.6
- References files using `@` mentions (e.g., `@"filename.gs"` or `@filename.py`) to indicate which files the assistant should open and work on. Confidence: 0.7
- Wants precise, explicit confirmation of exactly which files were changed and which were left untouched after a code modification, rather than a summary of what was done. Confidence: 0.5
- Prefers **silent/graceful handling** of unsupported message types (media, reactions, empty bodies) — silently drop with a 200 OK rather than sending error responses to users. Confidence: 0.6
- Requests comprehensive, cross-cutting refactoring — when a data model changes (e.g., single course → multi-course), expects ALL related code paths (data parsing, profile normalization, intercept handlers, system prompts) to be updated, not just the originating fetch function. Confidence: 0.7
- Prefers Apps Script (the data layer) to return raw structured JSON (e.g., `{"courses": ["SEN 301", "ECO 310"]}`) rather than pre-formatted text strings, so the consuming Python/LLM layer can interpret and format the data itself. Confidence: 0.8
- Expects sheet/row lookups to scan ALL matching rows and aggregate data (e.g., collect all course codes from every row matching a user), rather than stopping at the first match and returning a single value. Confidence: 0.8
- Prefers replacing hardcoded rule-based/if-else keyword-matching logic with an LLM-powered conversational brain for user interaction, to achieve fluid, natural conversation rather than robotic one-liners. Confidence: 0.8
- Designs system prompts with explicit, detailed persona definitions and strict behavioral guardrails (conversational intelligence rules, fact-guardrail constraints, graceful "warmly explain if data is missing" fallback patterns). Confidence: 0.8
- Favors a moderate temperature setting (e.g., 0.4) to balance "natural linguistic variety and conversational warmth" with low hallucination risk. Confidence: 0.7
- Prefers graceful, warm fallback behavior when data is unavailable — instructs systems to warmly explain that the information isn't accessible rather than guessing or fabricating facts. Confidence: 0.7
- Expects all previously working data sources and functionality to be preserved during architectural refactoring — silently dropping a data path (e.g., monthly lessons data) when replacing rule-based intercepts with an LLM is a defect, not an acceptable simplification. Confidence: 0.6
- Wants to understand the reasoning behind significant architectural changes — asks "why" when intercepts or logic are removed/refactored, expecting a detailed explanation of the rationale rather than just accepting the change. Confidence: 0.6
- Pragmatic and context-aware about risk — distinguishes between different subsystems (interactive bot vs. batch daemon) and only applies safety measures (e.g., cold-contact filtering) where the actual threat exists, not universally. Prefers minimal, targeted solutions over blanket defenses. Confidence: 0.6
- Avoids redundant fallback mechanisms when the primary solution is already reliable — e.g., no need for a fuzzy name matcher as backup when LID-to-phone conversion works perfectly. Not a fan of over-engineering with unnecessary defensive layers. Confidence: 0.6
- Expects a comprehensive, organized end-of-session report summarizing every change made, structured by file with clear categories (tables/groups), when explicitly requesting "a report of what you have achieved." The report should be scoped to the current session/day's work only, not the entire cumulative project history. Confidence: 0.6
- Provides structured diagnostic troubleshooting as numbered checklists with specific time-window tolerances and edge-case explanations, rather than vaguely reporting symptoms — proactively tells the assistant what likely culprits are and what precise ranges/conditions to check. Confidence: 0.6
- Prefers performance-optimized logic with early-exit / fast-fail patterns — flips data-access order so the cheapest/lightest check runs first, and expensive operations (like reading a spreadsheet) only execute when actually needed. Explicitly designs "flipped logic" to minimize I/O and avoid timeouts. Confidence: 0.7
- Understands and explains multi-layer timeout topology — distinguishes between client-side timeout (e.g., Python `requests` timeout), edge-server timeout (e.g., Google's 504 Gateway Timeout), and server-execution timeout, and addresses each at its appropriate layer rather than conflating them. Confidence: 0.7
- Advocates pragmatic two-phase remediation: apply a temporary buffer fix (e.g., raise timeout from 30s to 60s) to stop immediate failures, while simultaneously deploying the permanent architectural fix (e.g., fast-exit logic in the server). Rejects doing only one or the other as incomplete. Confidence: 0.8
- Prefers extracting meeting/class links from calendar events using a prioritized multi-source fallback chain: native `getHangoutLink()` → description regex scraping → `getLocation()` → sheet/profile fallback. Rejects checking only the location field. Confidence: 0.7
- Cares about idempotent processing in automated polling/daemon systems — explicitly diagnoses duplicate-message bugs by analyzing the polling-window math (e.g., 30-min window ÷ 5-min poll interval = 6 potential sends), and expects deduplication via unique ID tracking in the database (MongoDB compound indexes, sent-reminder collections) rather than relying on state-less time windows or message-layer dedup. Confidence: 0.7
- Anti-ban conscious — proactively wants human-like timing between automated WhatsApp/WAHA dispatches (random delays of 10-25 seconds between messages) to avoid platform flagging and bans, not just dedup of content. Confidence: 0.7
- Prefers querying calendar events anchored to start-of-day (00:00) rather than the current time, with a wider lookahead window (e.g., 7 days), to prevent "schedule amnesia" where events later in the same day are missed due to query timing or timezone shifts. Confidence: 0.7
- Prefers to keep tooling/configuration/IDE-specific directories (e.g., `.commandcode/`) out of version control by explicitly adding them to `.gitignore`. Confidence: 0.6
- Wants the assistant to provide concrete, copy-paste-ready terminal commands (e.g., `git init`, `git push ...`) for version control operations, not just verbal explanations of what to do. Confidence: 0.6
